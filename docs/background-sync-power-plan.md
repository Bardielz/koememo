# 后台同步恢复与离电录音优化方案

目标是在手表离电录音 8–12 小时期间允许手机离开、锁屏或暂停接收。恢复后，每个已关闭片段都应能在手机上校验并播放。验收分别记录录音续航、同步积压时间以及两端传完同一批音频的总耗电。

## 基线

- 11 月 23 日，Watch5 用 VOICE_RECOGNITION、48 kHz、Opus 32 kbps 且开启诊断，离电录音 7 小时 55 分 53 秒。约 500 万次阶段计时。编码输入与取输出占采集线程已测 CPU 的 67.3%。一次封装写入耗时 1.10 秒；949 次周期同步总共只用约 2.7 秒线程 CPU。
- 11 月 24 日，同一配置离电录音 8 小时 1 分 55 秒。97 段保存在手表，检查时手机没有该批次文件或临时文件。手表记录 13 次同步尝试，10 次通道异常、3 次等待请求超时。重试中存在对历史文件的重复确认。
- 手机切后台期间，一次设计上最多 8 秒的退避，经过时间达到 2 小时 12 分。最后一轮手机停在读目录，手表发完目录后等待约 181 秒。系统终止手机进程发生在该次超时约 4 分钟后。初次通道断开的原因、整机深睡与单进程调度延迟的贡献仍待区分。

## 第一批：低开销观测和有界恢复

1. 在手机 SyncService、手表 AudioTransferSession 和共享 SyncMetrics 中关联两端尝试。当前 attempt 由两端分别生成，增加可协商的共享尝试编号；旧版对端继续使用现有路径，按 session 和时间关联。目录阶段记录首字节、条目数、读取完成及首个请求。错误记录最后进展、片段标识、偏移、通道关闭原因和应用错误码。摘要在阶段切换、超时、退出时写入；字节计数在内存累计。详细指标沿用两端实验开关。
2. 退避开始和结束同时记录 elapsedRealtime 与 uptimeMillis。两者增量之差估计整机深睡；其余延迟再通过服务生命周期与进程退出信息核对。将预期唤起时间与实际时间持久化，下一次运行也能解释中断。
3. 手机持久化待同步任务，区分用户暂停、等待设备、正在传输和完成。每台表同时只允许一个传输任务。短暂中断沿用有限退避；唤醒后若已过期，丢弃旧通道，按已落盘断点重新协商。重试用尽后释放资源，保留队列，下次用户进入或系统允许的调度机会继续。用户主动暂停应取消自动恢复。手机侧设有界无进展超时，覆盖阻塞读取；由独立计时器关闭本次通道，使工作线程能退出。
4. 保留接收端临时文件、长度及 SHA-256 校验、原子改名和提交后回执。测试杀进程时覆盖三个窗口：写到一半、改名后未回执、回执已发但对端未收到。重复回执不得生成重复文件。手表继续独立录音。

## 第二批：减少恢复成本与诊断成本

- 手表目前每次连接都遍历 events.jsonl 重建目录，连同大量无关遥测一起解析。为已关闭片段维护可重建的轻量索引；先按版本和文件位置增量读取，处理日志截断、最后一行写入不完整与升级前数据。按页发送，先让手机请求一页。手机保存已校验文件的索引，对新下载、文件变化或显式完整性检查再算哈希。手机文件被删除时应能重传，手表历史回执不能代替本次手机库存。
- 自动补传可按批次限制时间或字节数，优先保证录音。允许手动同步和充电时集中同步。先用现有 Data Layer 比较两种同步时机，再决定是否值得增加 Wi-Fi 通道。
- 录音先做相同配置下诊断开关 A/B。若诊断开销可重复测出，对高频编解码操作抽样计时，将调用总数与计时样本数分开。封装写入保留低成本时钟，以便捕获单次长停顿，只在超阈值时附记片段号、边界及采样时间。周期落盘保持 30 秒。
- 小范围测试并记录亮屏区间、两端同步字节、重传、充电状态、线程 CPU 和电荷计数。同步计时与录音计时使用同一单调时间轴。整机电量和电荷计数用于组间比较；线程 CPU 用于定位代码热点。编码格式、采样率和传输方式分别做单变量实验。

## 验收顺序

| 场景 | 检查项 |
| --- | --- |
| 手机前台、同批音频基线 | 记录唯一片段数、哈希、有效字节、耗时和两端电荷差；先验证正常流程 |
| 手机锁屏、退后台、离开后重连 | 与前台使用相同输入；能从持久化任务恢复，无并发重试，已完成文件无需重复发送正文 |
| 断开通道、终止接收进程、丢失回执 | 重放三个中断窗口，最终唯一文件集与源清单一致；用户暂停后保持暂停 |
| 仅录音，诊断关与开 | 同一设备、起始电量区间、配置及屏幕条件，关闭无线调试，交替重复短测，比较每小时耗电及有效音频时长 |
| 录音期间同步与结束后集中同步 | 分别记录手表录音阶段续航，以及到同批文件全部送达时两端总电耗、完成延迟、可解码时长和缺段 |
| 8–12 小时真机验收 | 97 段作为现有恢复样本先校验；另做新长录。核对清单、哈希、解码、异常时间窗和保护停止原因 |

首轮不引入全天唤醒锁、无限重试或全局延长超时。若双时钟与受控对照将停顿定位为深睡，再单独试验只覆盖活跃传输、有硬超时的手机端唤醒锁，记录额外耗电，断线和退避时立即释放。

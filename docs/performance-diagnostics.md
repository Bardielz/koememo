# 性能诊断与耗电对照

## 使用

暂停并等待保存后，在设置中开启实验功能，再开启性能诊断；下一轮录音生效。总开关关闭会禁用诊断但保留选项。诊断会增加开销，常规录音及续航测量应关闭。不会自动启动录音、追踪或上传数据。

每轮开始记录应用版本、配置、诊断状态；音频初始化记录编码器名称、软件/硬件及供应商属性。开始、每分钟和结束记录充电状态、电荷计数、原始电流、电压与温度。缺失的字段省略，不以零代替。OEM 电流单位与精度尚未校验，不能直接计算 mW；电荷计数也需要验证更新分辨率。

开启诊断后，捕获线程每分钟及 writer 关闭后记录 `performance` 事件：

- `capture_read`：包含阻塞等待的麦克风读取。
- `level`：音量计算及观察者回调。
- `encoder_input`：等待输入缓冲、复制 PCM、提交数据；不是编码算法本身的 CPU 时间。
- `encoder_output_wait`：取得编码输出缓冲的调用，包括等待。
- `output_copy`：复制编码输出。
- `write_and_package`：容器封装和缓冲写入，包括切段关闭时的同步、哈希和事件记录。
- `sync`：周期刷新与文件同步，包含封装器刷新剩余页面。
- `close`：最终关闭，包括尾页、同步、哈希和片段事件。

`*_calls` 为次数；`*_wall_ns` 为累计经过时间；`*_cpu_ns` 为当前捕获线程累计 CPU 时间；`*_max_wall_ns` 为最长一次经过时间。计数每轮重置，各报告均累计，不能将每分钟快照相加。停止时 `final=true`；异常退出时可能仅有不完整的中间快照。

```sh
python3 tools/audio/diagnostics.py /path/to/events.jsonl
```

此工具选每轮最后一次快照，区分完整和不完整报告。旧日志没有诊断事件时返回空列表，不虚构统计。

## 解释边界

等待耗时不是 CPU 耗时，CPU 时间也不是能量。MediaCodec 可能在系统进程运行，必须用短时 Perfetto 配合分析系统编码器与音频服务。各阶段只是已标记部分，不构成整轮完整账本，也不能精确拆分麦克风、CPU 与存储的 mWh。

关闭诊断时不读取阶段时钟，不打 trace 标记，不生成 performance 事件，不使用 writer 装饰器。开启后的 trace 段使用 `KoeMemo/` 前缀，只有外部追踪启用对应应用时才会采集；应用不自动开启系统追踪。

## 对照方案

1. 固定设备、版本、音源、码率、屏幕/无线状态和可重复的音频场景。停止充电，温度稳定后开始。
2. 保持 Opus 32 kbps 不变，比较 16/24/48 kHz；随后在相同采样率比较 AAC/Opus，注明码率差异。不要将两种变化混为单变量实验。
3. 每组重复至少三次并交换顺序；以电荷计数有效分辨率决定测试时长，比较相近电量区间。缺失或不可信的计数不能用于能耗结论。
4. 短时诊断定位热点，正式离电测试关闭诊断和无线调试；结束后再连接导出。追踪开启与关闭的开销需单独对照。
5. 同时检查音频哈希、结构、完整解码、分段衔接及试听。优化不能通过丢音、延迟保存或改变录音目标来获取表面收益。

本次保留 PCM 批次、编码器超时、32 KiB 写缓冲、30 秒同步、500 ms 音量计算和唤醒锁策略。只有测到热点后才调整这些参数。本功能尚未证明任何耗电下降。
